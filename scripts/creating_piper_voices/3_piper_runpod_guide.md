# Piper TTS - Training on RunPod (stage 3)

NOTE: this document was generated by Claude. This guide has been tested with medium voice, not high.
Plase check all the info to assure their truthfulness.

A complete, reusable guide to training a Piper voice from a dataset you have
already recorded and preprocessed locally.

**Assumption**: you have a `<voice>.7z` archive containing `wavs/` (mono WAV,
22050 Hz, 16 bit) and `metadata.csv` in LJSpeech format, both already passed
through `piper_preprocess.py`.

In every command, replace `<voice>` with the name of your voice.

---

## 0. RunPod concepts

Four things to understand before clicking anything, because getting them wrong
costs either money or work.

**Community Cloud vs Secure Cloud.** Community pods run on GPUs owned by private
hosts, cost roughly 10-30% less, and are isolated only at the container level.
Secure pods live in RunPod's own T3/T4 datacentres on single-tenant machines, and
that is the tier the SOC 2 / ISO 27001 / PCI DSS certifications apply to.

For training a TTS voice from your own recordings: **Community**. For fine-tuning
on client data: Secure, EU region, anonymised data.

**On-Demand vs Spot.** Spot is cheaper but the pod can be terminated without
warning. For training, use **On-Demand**: the saving is a few dollars, and with
Spot you have to reconnect and restart by hand every time.

**Container disk vs Volume disk.** The container disk, including the home
directory `~`, is wiped on every stop and restart. The volume disk is mounted at
`/workspace` and is persistent. **Every path in this guide uses `/workspace`**:
never use `~`, or you lose everything at the first reboot.

**Stop vs Terminate.** Stop freezes the pod but you keep paying for storage.
Terminate destroys the pod and its volume. When the work is done: download your
files first, then Terminate.

## 1. Local preparation (Windows)

### runpodctl

This is what moves files to and from the pod without configuring SSH. It handles
large transfers better than `scp` does over thousands of small WAV files.

```powershell
# Install by downloading the executable from GitHub, then run this script:
$dir = "$env:USERPROFILE\Downloads\Runpod"

# Add the folder to the user PATH, avoiding duplicate entries
$userPath = [Environment]::GetEnvironmentVariable('Path', 'User')
if (($userPath -split ';') -notcontains $dir) {
    [Environment]::SetEnvironmentVariable(
        'Path',
        ($userPath.TrimEnd(';') + ";$dir"),
        'User'
    )
}

# Shim so the command is just "runpodctl", regardless of the exe file name
@'
@echo off
"%~dp0runpodctl-windows-amd64.exe" %*
'@ | Set-Content -Encoding ASCII "$dir\runpodctl.cmd"

# Check
runpodctl version
```

Then configure your API key, which you generate at runpod.io under
Settings → API Keys:

```powershell
runpodctl doctor --apiKey <your_api_key>
```

### Checking the archive

Before uploading, make sure the counts match:

```powershell
(Get-ChildItem .\wavs\*.wav).Count
(Get-Content .\metadata.csv).Count
```

They must return the same number. If they do not, stop here: a mismatch between
WAV files and transcriptions produces a training run that goes for hours without
a single error and yields a voice that pronounces random words.

## 2. Creating the pod

1. **Pods → Deploy**
2. GPU: **RTX 4090**, filtered to **Community Cloud**
3. Check that the offer has at least **8 vCPUs and 32 GB of RAM**. The
   `piper_train` dataloader does a lot of work on the CPU, and with 4 vCPUs the
   GPU spends its time waiting. Offers vary a great deal on this point.
4. Template: look for the official PyTorch one with py3.10 / cuda12.1. If it is
   not listed, create a custom template with this container image:

   ```
   runpod/pytorch:2.2.0-py3.10-cuda12.1.1-devel-ubuntu22.04
   ```

   It has to be the **devel** variant, not `runtime`: `nvcc` is needed to compile
   `monotonic_align` with Cython.
5. **Container disk**: 20 GB. **Volume disk**: 60 GB, mount path `/workspace`.
   Checkpoints are almost 1 GB each.
6. **HTTP ports**: add **6006** for TensorBoard. Ports cannot be added later, so
   forgetting this means recreating the pod.
7. Deploy.

```bash
ssh ...@ssh.runpod.io -i $env:USERPROFILE\.runpod\ssh\runpodctl-ssh-key
```

## 4. Setting up the environment

Put everything in a script on `/workspace`, so that if the pod restarts you can
redo it with one command instead of by hand.

```bash
cd /workspace
cat > setup.sh << 'EOF'
#!/bin/bash
set -e

# System deps. espeak-ng is the phonemiser Piper relies on.
# p7zip-full is needed to extract the .7z dataset archive.
apt update && apt install -y espeak-ng git build-essential p7zip-full

# Virtualenv WITH access to the image's preinstalled torch
cd /workspace
python3 -m venv --system-site-packages piper-env
source piper-env/bin/activate

pip install --upgrade pip

# piper-phonemize is not on PyPI, install from the GitHub wheel
pip install piper-phonemize~=1.1.0 \
  --find-links https://github.com/rhasspy/piper-phonemize/releases/expanded_assets/v1.1.0

# NOTE: torch is deliberately NOT installed here. The image already ships
# 2.2.0+cu121 and reinstalling would pull a newer, incompatible version.

pip install pytorch-lightning==1.9.5
pip install torchmetrics==0.11.4
pip install librosa onnxruntime cython tensorboard
pip install onnx
pip install "numpy<2.0"


# Old rhasspy repo: the OHF-Voice fork is not checkpoint-compatible
if [ ! -d /workspace/piper-old ]; then
  git clone https://github.com/rhasspy/piper.git /workspace/piper-old
fi

cd /workspace/piper-old/src/python
pip install -e . --no-deps

# Build the Cython monotonic_align extension required by VITS
cd /workspace/piper-old/src/python/piper_train/vits/monotonic_align
cython core.pyx
python3 -c "from setuptools import setup; from Cython.Build import cythonize; setup(ext_modules=cythonize('core.pyx'))" build_ext --inplace
mkdir -p monotonic_align
cp "$(find build -name 'core*.so' | head -1)" monotonic_align/

echo "Setup complete."
EOF

chmod +x setup.sh
./setup.sh
```

`--system-site-packages` is the detail that matters: it creates the virtualenv
but lets it see the torch already installed in the image, so you do not download
it again.

### Verifying

```bash
source /workspace/piper-env/bin/activate
python3 -c "import torch; print(torch.__version__, torch.cuda.is_available())"
python3 -c "import pytorch_lightning as pl; print(pl.__version__)"
ls /workspace/piper-old/src/python/piper_train/vits/monotonic_align/monotonic_align/
```

Expected: `2.2.0+cu121 True`, then `1.9.5`, then a file named
`core.cpython-310-x86_64-linux-gnu.so` or `core.cpython-311-x86_64-linux-gnu.so`,
depending on the Python version in use.

### Activating automatically

```bash
echo 'source /workspace/piper-env/bin/activate' >> ~/.bashrc
```

This has to be redone after every pod restart, because `~/.bashrc` lives on the
container disk.

```bash
mkdir -p /workspace/piper-checkpoints
curl -L -o /workspace/piper-checkpoints/lessac-medium.ckpt \
  "https://huggingface.co/datasets/rhasspy/piper-checkpoints/resolve/main/en/en_US/lessac/medium/epoch%3D2164-step%3D1355540.ckpt"
```

```bash
# Does NOT work: returns 403
wget "https://huggingface.co/datasets/rhasspy/piper-checkpoints/resolve/main/en/en_US/lessac/medium/epoch%3D2164-step%3D1355540.ckpt" \
```

For a **high** voice the checkpoint would be `en_US-lessac-high` or `ryan-high`,
and `--quality high` would be needed in both preprocessing and training. See

## 7. Piper preprocessing

This runs on the CPU and takes a few minutes. Do it on the pod rather than
locally: that avoids uploading the `.pt` cache, which is heavier than the WAV
files themselves, and it avoids the problem of absolute paths baked into
`dataset.jsonl`.

```bash
cd /workspace/piper-old/src/python

OMP_NUM_THREADS=1 \
python3 -m piper_train.preprocess \
  --language it \
  --input-dir /workspace/piper-datasets/<voice> \
  --output-dir /workspace/piper-training/<voice> \
  --dataset-format ljspeech \
  --single-speaker \
  --sample-rate 22050 \
  --max-workers 4
```

Set `--language` to the language of your dataset, not to the language of the
starting checkpoint. With 4 workers and around 950 clips, expect roughly 5 to 10
minutes.

**Why `OMP_NUM_THREADS` and `--max-workers` are both set.** `OMP_NUM_THREADS`
tells each process how many threads it may use for its internal numerical work
in numpy, librosa and torch on the CPU. The default is "every available core".

The problem is multiplicative: launch 8 workers, each convinced it can use 8
cores, and you get 64 threads fighting over 8 cores. They spend more time
switching than working, and preprocessing ends up slower than with a single
worker. This is called oversubscription. Setting it to 1 forces every worker to
be single-threaded, so the only parallelism left is the one you control with
`--max-workers`.

The right value for `--max-workers` depends on the vCPUs available, which is
fixed when you rent the pod. It is worth waiting for an offer with 12 vCPUs.
Both stages benefit: preprocessing because it runs entirely on the CPU, and
training because the dataloader reads tensors from the cache and packs them into
batches on the CPU. With too few vCPUs the GPU waits for data, and you pay for it
without using it.

Expected output in `/workspace/piper-training/<voice>/`: `cache/`, `config.json`
and `dataset.jsonl`.

## 8. Smoke test (two minutes, do not skip it)

This exists to surface any incompatibility between torch 2.2 and
pytorch-lightning 1.9.5 immediately, rather than three hours into a training run.

```bash
cd /workspace/piper-old/src/python

python3 -m piper_train \
  --dataset-dir /workspace/piper-training/<voice> \
  --accelerator gpu --devices 1 \
  --batch-size 32 \
  --validation-split 0.0 --num-test-examples 0 \
  --max_epochs 2167 \
  --resume_from_checkpoint /workspace/piper-checkpoints/lessac-medium.ckpt \
  --checkpoint-epochs 1 --precision 32
```

`--max_epochs` is 2167 because the lessac medium checkpoint closes at epoch 2164:
ask for fewer and the trainer refuses to start at all.

If it completes two epochs and writes a checkpoint, you are in good shape. If it
blows up with errors about `pytorch_lightning` or `torch.distributed`, see the
troubleshooting section.

Before launching the real training run, delete the test checkpoints:

```bash
rm -rf /workspace/piper-training/<voice>/lightning_logs
```

## 9. Training

Three tmux windows: training, checkpoint cleanup, TensorBoard.

### Window 1 - training

```bash
cd /workspace/piper-old/src/python

python3 -m piper_train \
  --dataset-dir /workspace/piper-training/<voice> \
  --accelerator gpu --devices 1 \
  --batch-size 32 \
  --validation-split 0.0 --num-test-examples 0 \
  --max_epochs 10000 \
  --resume_from_checkpoint /workspace/piper-checkpoints/lessac-medium.ckpt \
  --checkpoint-epochs 5 --precision 32
```

`--checkpoint-epochs 5` rather than 1: with around 950 clips an epoch is short,
and saving on every one of them would fill 60 GB in a few hours.

If you run out of VRAM, drop to `--batch-size 16`. Halving the batch size means
you need proportionally more epochs to reach the same number of steps.

### Window 2 - automatic cleanup (`ctrl+b` `c`)

```bash
VOICE=<voice>
while true; do
  cd /workspace/piper-training/$VOICE/lightning_logs/version_0/checkpoints/ 2>/dev/null && \
  ls -t *.ckpt 2>/dev/null | tail -n +6 | xargs -r rm --
  sleep 600
done
```

This keeps only the five most recent checkpoints. Without it, the disk fills up
overnight and training stalls.

***Note: this loop is unnecessary with the training command above, which by
default keeps a single checkpoint.***

### Window 3 - TensorBoard (`ctrl+b` `c`)

```bash
tensorboard --logdir /workspace/piper-training/<voice>/lightning_logs \
  --host 0.0.0.0 --port 6006
```

`--host 0.0.0.0` is mandatory: by default TensorBoard listens on localhost only,
and RunPod's proxy would be refused.

Then, from the pod page: **Connect → HTTP Service port 6006**.

### Window 4 - checkpoint watch (`ctrl+b` `c`)

```bash
ls -t /workspace/piper-training/<voice>/lightning_logs/version_1/checkpoints/*.ckpt | wc -l
df -h /workspace
```

There should be 5, at most 6 if the first cleanup cycle has not run yet.

### Resuming after an interruption

```bash
# find the most recent checkpoint
ls -t /workspace/piper-training/<voice>/lightning_logs/version_0/checkpoints/ | head -1
```

Then relaunch the same training command with `--resume_from_checkpoint` pointing
at that file. As long as you always resume from a checkpoint of the same version,
pytorch-lightning continues in `version_0` instead of creating a new one.

## 10. Monitoring

### Steps, not epochs

The unit of work is the **step**, not the epoch. One epoch contains
`clips / batch_size` steps, so with around 950 clips and a batch size of 32 you
get roughly **30 steps per epoch**.

| Steps | Epochs (~950 clips, batch 32) | What to expect |
|---|---|---|
| 10,000 | ~330 | already listenable, prosody still shaky |
| 20,000 | ~670 | good quality |
| 25,000-30,000 | 830-1000 | the finish line |
| beyond 35,000 | 1170+ | overfitting risk below 2 hours of audio |

The epoch counter in the checkpoint file names shows high numbers because it
includes lessac's own: **subtract about 2165** to get the epochs your training
actually ran.

Figures like "1000 to 2000 epochs" from Piper tutorials assume datasets of 20 to
30 minutes and do not transfer.

### The losses

- `loss_mel` correlates best with perceived quality, but it is not plotted in
  TensorBoard.
- `loss_gen_all` goes down, but it flattens out long before the voice is ready.
- `loss_disc_all` oscillates by design and is not a quality indicator.

With `--validation-split 0.0`, TensorBoard **generates no validation audio**. The
losses only tell you whether training is healthy, not whether the voice is ready.
That judgement is made with your ears.

### The listening loop

1. Prepare 6 to 8 fixed test sentences, always the same ones, covering the hard
   cases: numbers, proper nouns, a question, a long sentence with commas,
   accented words, an abbreviation.
2. Every ~5000 steps, export the current checkpoint to ONNX. The export runs on
   the CPU, so you can also download the `.ckpt` and do it locally.
3. Synthesise the same sentences and listen to them in sequence.
4. When two or three consecutive exports bring no audible improvement, you are
   done.

What to listen for, in the order it appears: first the metallic background noise
disappears, then prosody stabilises as pauses and intonation stop being random,
and last the pronunciation of the hard cases settles. If the intonation still
wobbles, the voice is not ready, no matter how flat the loss curve looks.

**The best checkpoint is often not the last one.** Do not delete good
intermediate ones.

## 12. Cost

As an order of magnitude, a voice built from 1 to 2 hours of audio on a
Community RTX 4090 takes **6 to 12 hours and costs roughly 3 to 5 dollars**.

For an exact figure, watch the training output during the first half hour, note
how many seconds an epoch takes, and multiply by the number of epochs you need.

Three things account for most overspending:

- **a pod left running** after training finished (set an alarm)
- **a volume left undeleted**, which keeps costing money with the pod stopped
- **confusing Stop with Terminate**

If you have several voices to train, **run one pod per voice in parallel**. The
total GPU-hours are identical but you finish in a third of the calendar time.
Moving up a GPU tier costs more and returns less, because at batch size 32 you
would not saturate an A100 anyway.

## 13. Differences for a high voice

This section lists **only what changes** compared to the medium procedure above.
Anything not mentioned here stays exactly the same.

### What does not change

- **Sample rate**: high quality in Piper is still **22050 Hz**, exactly like
  medium. The local `piper_preprocess.py` step (denoise, trim, LUFS, mono 22050)
  needs no changes.
- Dataset format, the `.7z` archive, uploading with `runpodctl`, tmux, `setup.sh`,
  the smoke test, ONNX export, cleanup and terminating the pod.

### What changes

**1. Starting checkpoint**

```bash
mkdir -p /workspace/piper-checkpoints
curl -L -o /workspace/piper-checkpoints/lessac-high.ckpt \
  "https://huggingface.co/datasets/rhasspy/piper-checkpoints/resolve/main/en/en_US/lessac/high/epoch%3D2218-step%3D838782.ckpt"
```

This checkpoint closes at **epoch 2218**, which has two consequences:

- the smoke test needs `--max_epochs 2221` (2218 closed, plus 2 test epochs, plus
  1 for margin), otherwise the trainer refuses to start;
- in section 10, the epoch counter has to be corrected by subtracting about
  **2219** instead of about 2165.

The `step=838782` in the file name is lessac's history and **does not count
toward your own total**: the step counter restarts from zero, exactly as it did
with the medium checkpoint.

**2. Preprocessing**

```bash
OMP_NUM_THREADS=1 \
python3 -m piper_train.preprocess \
  --language it \
  --input-dir /workspace/piper-datasets/<voice> \
  --output-dir /workspace/piper-training/<voice> \
  --dataset-format ljspeech \
  --single-speaker \
  --sample-rate 22050 \
  --audio-quality high \
  --max-workers 8
```

`--audio-quality` is **only a label**. It ends up in `config.json` and from there
in the `.onnx.json`, and changes nothing about how the audio is processed. Set it
anyway, because that config travels with the finished model.

`--max-workers 8` halves the time compared to 4, provided you picked a pod with
at least 8 vCPUs. With around 2300 clips this takes it from roughly 30 minutes
down to roughly 15.

**3. Training**

```bash
python3 -m piper_train \
  --dataset-dir /workspace/piper-training/<voice> \
  --accelerator gpu --devices 1 \
  --quality high \
  --batch-size 32 \
  --validation-split 0.0 --num-test-examples 0 \
  --max_epochs 10000 \
  --resume_from_checkpoint /workspace/piper-checkpoints/lessac-high.ckpt \
  --checkpoint-epochs 5 --precision 32
```

`--quality high` is **mandatory**. Without it the trainer builds a medium model
and resumes it from high weights: either it blows up with a dimension mismatch,
or it runs and hands you a wrong result.

**4. VRAM and batch size**

The high model has roughly twice the parameters of the medium one, 28-32M against
15-20M. With `--precision 32` and batch size 32 you can hit out-of-memory on a
24 GB 4090. Check during the first two minutes:

```bash
watch -n 5 nvidia-smi
```

Above 90% VRAM, drop to `--batch-size 16`, remembering that halving the batch
means twice the epochs for the same number of steps.

**5. `--precision 16` (optional, needs testing)**

It can nearly double the speed and halves VRAM use, but VITS in fp16 sometimes
diverges. The protocol:

1. run the smoke test at `--precision 16`;
2. launch the real training and watch the losses for the first **1000 to 2000
   steps**;
3. if `nan` or `inf` appear, kill everything and restart from scratch at
   `--precision 32`;
4. if the numbers are still normal after 2000 steps, it will hold for the whole
   run.

If you would rather not babysit it, stay at 32: you lose time and money, but you
sleep.

**6. Multi-GPU: no**

With `--devices 2`, pytorch-lightning uses DDP, which **does not divide the steps,
it multiplies the effective batch size**. You change the convergence dynamics
instead of finishing sooner. Real-world scaling on VITS is around 1.6-1.7x for
twice the cost, and DDP on torch 2.2 with lightning 1.9.5 is precisely where the
`torch.distributed` errors come from.

If you have two voices to train, **one pod per voice in parallel**: same
GPU-hours, half the calendar time.

**7. Choosing the pod**

Among 4090 offers, what varies is vCPUs and RAM. VRAM is always 24 GB. Above
32 GB of RAM the exact figure makes no difference, so the real selection
criterion is **the number of vCPUs**: the `piper_train` dataloader runs on the
CPU, and with too few cores the GPU waits for data for the entire length of the
run, not only during preprocessing.

The typical symptom of a CPU-starved pod: the GPU sits at 50-60% instead of near
100%, while every core is pinned.

### What to expect with ~2300 clips / 3.6 hours of audio

| Voice | Clips | Steps per epoch (batch 32) | Duration | Indicative cost |
|---|---|---|---|---|
| medium, 1.2h | ~950 | ~30 | 4-6 hours | $2-3 |
| high, 3.6h | ~2300 | ~72 | 15-20 hours | $8-12 |

The finish line is around **60,000 to 80,000 steps**. Start exporting and
listening from **30,000**, which is where the medium voice was already
presentable.

The "overfitting risk beyond 35,000 steps" note in section 10 applies to datasets
under 2 hours. With 3.6 hours you have far more room to run long.

## 14. Common problems

**`no kernel image is available for execution on the device`**
A Blackwell GPU (RTX 5090, RTX PRO 6000, B200) with cu121 wheels. Change GPU and
stay on Ada or Ampere.

**Errors about `pytorch_lightning` or `torch.distributed` during the smoke test**
An incompatibility between torch 2.2 and lightning 1.9.5. Try dropping to an
image with torch 2.0 or 2.1, still cu121 and py3.10.

**`ModuleNotFoundError: monotonic_align`**
The Cython build failed, or the `.so` is not in the right folder. Check the exact
path: the file name depends on the Python version.

**Disk full halfway through training**
Automatic cleanup was not running, or `--checkpoint-epochs` is too low. Delete the
old checkpoints and resume from the most recent one.

**TensorBoard does not load**
Either `--host 0.0.0.0` is missing, or port 6006 was not declared when the pod was
created. In the second case the pod has to be recreated.

**Everything gone after a restart**
You used `~` instead of `/workspace`. Only `/workspace` is persistent.

**Warnings about incompatible versions of pytorch-lightning, torch and cython**
Expected and harmless, as are the `FutureWarning` messages about `torch.load`
with `weights_only=False`, which are fine for checkpoints you trust.
